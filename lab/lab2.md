## Question 2

`--backend-store-uri sqlite:///mlflow.db` tells MLflow where to store the run metadata.

The metadata includes information such as:
- experiment names
- run IDs
- parameters
- metrics
- timestamps
- run status

In my setup, this metadata is stored in the local SQLite database file `mlflow.db`.

`--default-artifact-root ./mlruns` tells MLflow where to store run artifacts.

Artifacts are files produced by a run, such as:
- trained models
- saved plots
- output files

The main difference is:

- Metadata describes the experiment and its results.
- Artifacts are the actual files produced by the experiment.


## Question 3

`mlflow.db` and `mlruns/` should not be tracked by Git because they are local experiment outputs, not source code.

`mlflow.db` contains MLflow tracking metadata, and `mlruns/` contains artifacts generated by experiment runs.

They also should not be tracked by DVC because they are not versioned datasets used as project input. They are generated experiment results that can change after every training run.

Therefore, both should remain local and be ignored by Git and DVC.

## Question 5

`mlflow.log_param` is used to log fixed configuration values that are chosen before training, such as learning rate, batch size, number of epochs, dataset, and model architecture.

`mlflow.log_metric` is used to log values produced during or after training, such as training loss, validation loss, validation accuracy, and test accuracy.

`log_metric` accepts a `step` argument because metrics can change during training. In my script, the step represents the epoch number.

Parameters do not need a step because they stay fixed for the whole training run.

## Question 8

From the parallel coordinates plot, I observed that the learning rate had a strong effect on validation accuracy.

The run with `lr = 0.0001` and `batch_size = 32` achieved the highest validation accuracy of about 0.7108.

The run with `lr = 0.01` had much lower validation accuracy.

For `lr = 0.001`, changing the batch size from 32 to 64 gave similar results, but batch size 32 had a slightly higher final validation accuracy.

Therefore, in my experiments, a smaller learning rate gave better performance, while increasing the batch size did not improve the final validation accuracy.
